<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| SQL migration -> production AlloyDB | DDL creates durable audit and diagnostic storage. |
| Future writers -> `feed_audit_events` | Later storage/runtime code will insert actor, detail, and snapshots. |
| Feed hard delete -> audit history | Current-state `feeds` rows may disappear while audit rows remain. |
| Future readers/delivery -> audit payloads | Later consumers may expose JSON snapshots and diagnostic detail. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-02-01 | Repudiation | `feed_audit_events` delete survival | mitigate | Do not add `REFERENCES feeds(id)` or `ON DELETE CASCADE`; store `feed_id`, `feed_name`, `source_type`, `before_values`, and ordering fields in audit rows. |
| T-01-02-02 | Spoofing | `actor_id` column | mitigate | Add `feed_audit_events_actor_id_check` for canonical namespaces and require `actor_id TEXT NOT NULL`. |
| T-01-02-03 | Tampering | action vocabulary | mitigate | Add `feed_audit_events_action_check` for the exact approved action values. |
| T-01-02-04 | Information Disclosure | `status_reason_detail` | accept | Bound `feeds.status_reason_detail` and audit-row `status_reason_detail` to 2048 characters; no redaction is required in Phase 1 per D-15/D-16, and no read API is added here. |
| T-01-02-05 | Denial of Service | mutable current-state indexes | mitigate | Do not index `feeds.status_reason_detail`; add it to the HOT-protection guard. |
| T-01-02-06 | Tampering | outbound-delivery future compatibility | mitigate | Do not add webhook, dispatcher, attempt, retry, signature, or receiver columns; keep delivery derived from domain audit rows. |
</threat_model>
