<objective>
Implement the shared async storage semantics for runtime feed audit events.

Purpose: Phase 4 runtime behavior depends on storage being able to distinguish
meaningful failure/quarantine/recovery outcomes from lease mechanics and retry
maintenance. This plan adds the storage-level primitives and tests before any
collector runtime call sites are changed.

Output: previous-status lease carrier, bounded diagnostic-detail persistence,
and async `FeedStore` audit gates for `feed.failure_reported`,
`feed.quarantined`, and `feed.recovered`.
</objective>

<decision_coverage>
- D-01: Runtime failure event creation is gated by logical
  `(status, status_reason)` changes.
- D-02: Diagnostic-detail, retry timing, and failure-counter churn alone are
  no-event maintenance.
- D-03: Non-terminal abnormal combo changes emit `feed.failure_reported`.
- D-04: Threshold crossing emits one `feed.quarantined` event.
- D-05: Same-combo repeated attempts are intentionally no-event writes.
- D-06: Recovery is emitted only for successful runtime clearing of prior
  abnormal status.
- D-07: Abnormal recovery statuses are `failing` and `quarantined`; reset
  remains `feed.reset`.
- D-08: Claim/lease activity is not recovery.
- D-09: Detail-only clearing while prior status was normal is not recovery.
- D-10: Later lease release after recovery remains unaudited lease churn.
- D-15: Runtime storage accepts explicit semantic service actor IDs.
- D-16: No `system:` actor prefix is introduced.
- D-17: Source type is not encoded in `actor_id`.
- D-21: Runtime abnormal writes set canonical bounded detail.
- D-22: `status_reason_detail` follows `status_reason` lifecycle.
- D-23: Persisted detail is bounded and sanitized.
- D-24: `quarantine_reason` remains compatibility-only.
- D-25: Clean progress and lease mechanics do not create audit events.
- D-26: Clean success can update current state without audit.
- D-27: Ambiguous scheduler mechanics default to no audit event.
</decision_coverage>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Collector runtime -> FeedStore | Runtime passes causal actor and prior state; storage owns persistence and audit row construction. |
| FeedStore -> AlloyDB | Feed mutation and audit insert must commit or roll back together. |
| Diagnostic text -> storage | Runtime/provider exception text crosses into durable data and must be bounded and sanitized. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01-01 | Repudiation | Runtime actor attribution | mitigate | Require explicit actor_id for audited abnormal/recovery writes and test semantic service actors in later caller wiring. |
| T-04-01-02 | Tampering | Audit snapshots | mitigate | Use maintained feed-row snapshots from storage instead of runtime-synthesized before/after values. |
| T-04-01-03 | Information Disclosure | status_reason_detail | mitigate | Add persistence-boundary redaction and cap before storing raw diagnostic detail. |
| T-04-01-04 | Denial of Service | Audit volume | mitigate | Gate events by logical `(status, status_reason)` changes and suppress same-combo retries and clean heartbeats. |
| T-04-01-05 | Consistency | Mutation/audit dual-write | mitigate | Use one DB transaction for feed mutation and audit insert; no audit row on no-op or rollback. |
</threat_model>
