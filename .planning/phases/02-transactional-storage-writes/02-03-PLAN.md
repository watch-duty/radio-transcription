<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| FeedService -> FeedStore | Lifecycle service methods pass a fixed service actor into required storage parameters. |
| FeedStore -> AlloyDB transaction | Lifecycle state change, sequence allocation, and audit insert must share one transaction. |
| Existing feed row -> delete audit snapshot | Delete snapshots must cross from current-state rows into durable audit history before current rows are removed. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03-01 | Repudiation | `FeedStore.delete_feed` | mitigate | Capture `GET_AUDIT_FEED_SNAPSHOT_SQL` before `DELETE_FEED_SQL`, insert `feed.deleted` before hard delete, and test `{}` after_values per D-11. |
| T-02-03-02 | Tampering | `deactivate_feed` / `reset_feed` / `delete_feed` | mitigate | Use one connection transaction for each lifecycle mutation and raise on impossible partial results so rollback prevents drift. |
| T-02-03-03 | Spoofing | Lifecycle service methods | mitigate | Pass fixed `service:feeds-service`; no route body actor fields are added and storage still requires explicit `actor_id`. |
| T-02-03-04 | Information Disclosure | Lifecycle snapshots | mitigate | Reuse `_audit_snapshot` allowlist and tests from Plan 02; do not serialize worker, heartbeat, fencing, filename, or unclaimed-since fields. |
| T-02-03-05 | Tampering | Concurrent lifecycle operations | mitigate | Lock the target feed snapshot before mutation, then allocate sequence through the counter table in the same lock order. |
| T-02-03-06 | Repudiation | Missing actor on lifecycle calls | mitigate | Keyword-only `actor_id` has no default; service tests assert every lifecycle call supplies the Phase 2 actor. |
| T-02-03-07 | Tampering | Rollback drift after audit insert or delete failure | mitigate | Insert audit and hard delete in one transaction, and Plan 4 validates no leftover audit row on transaction failure. |
| T-02-03-08 | Tampering | Audit integrity after hard delete | mitigate | Keep audit rows delete-safe by not adding a cascading `feeds` foreign key and by preserving before snapshot identity fields. |
</threat_model>

<risks_dependencies>
- Depends on Plan 02 private audit helpers, transaction-capable tests, and the `_FEEDS_SERVICE_ACTOR_ID` constant.
- Risk: delete snapshots can be captured too late because `feed_properties` cascades after `feeds` deletion. Always lock/read the audit snapshot and insert `feed.deleted` before `DELETE_FEED_SQL`.
- Risk: lifecycle lock ordering can drift from update/create behavior. For existing-feed mutations, lock the feed snapshot first, then mutate state, then allocate sequence and insert audit.
</risks_dependencies>
