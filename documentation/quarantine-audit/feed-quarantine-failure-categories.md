## Specific Engineering Questions

### 1. Dev `system_unexpected_error` with `ffmpeg_exit_8`

There are 4 dev rows where the stored status is `system_unexpected_error` and the raw reason is `ffmpeg_exit_8`. All 4 correlated to Broadcastify stream HTTP 404 stderr. There are also 4 older dev `ffmpeg_exit_8` quarantine rows with missing `status_reason`; those have the same 404 stderr root cause. Current classifier behavior should record these as `stream_http_404` / `source_offline` rather than `system_unexpected_error`.

### 2. `pubsub_publish_failed` root causes

Retained quarantine telemetry contains 48 prod `pubsub_publish_failed` quarantines: 44 `bcfy_calls` and 4 `fire_notifications`. All retained nearby publish failures show the same concrete Pub/Sub error: `InvalidArgument: 400 Invalid data in message: Message failed schema validation` with reason `INVALID_BINARY_PROTO_MESSAGE`. That means the source capture succeeded and the failure happened after capture, at the producer/schema/message contract boundary. The retained logs do not prove whether the exact mismatch was deployed producer version drift, schema version drift, or publishing the wrong serialized message type.

Retained dev logs contain 686 `pubsub_publish_failed` attempts from VM workers, but zero matching dev `feed_quarantined` telemetry rows in the retained quarantine set. The prior count of 31 dev quarantines is not visible in the retained quarantine telemetry available to this investigation.

### 3. Prod `system_unexpected_error` with `ffmpeg_exit_8`

There are 14 prod rows where the stored status is `system_unexpected_error` and the raw reason is `ffmpeg_exit_8`. All 14 correlated to Broadcastify stream HTTP 404 stderr. There are also 13 older prod `ffmpeg_exit_8` quarantine rows with missing `status_reason`; those have the same 404 stderr root cause.

### 4. Prod `reconnect_exhausted`

There are 2 prod rows with `system_unexpected_error` and raw reason `reconnect_exhausted`, plus 1 older prod row with missing `status_reason`. All 3 are the same feed, `openmhz-wmata`. Nearby logs show repeated OpenMHz WebSocket upgrade failures: `Refused WebSockets upgrade: 403`. Each collector attempt exhausted 10 OpenMHz transport reconnect failures, then reported one feed failure. The feed-level failure budget still applies across repeated collector attempts; it is separate from the 10 reconnect attempts inside one collector attempt.

### 5. Prod `capture_timeout`

The single prod `capture_timeout` quarantine is `OR / Lake County Public Safety & Forestry` at `2026-06-08T20:04:02.343790Z`. The final attempt started ffmpeg, saw Broadcastify MP3 stream metadata for `https://partner.broadcastify.com/42359.mp3?burst=0`, opened a segment file, then produced no finalized segment within the 30 second read timeout and was force-killed. The same feed had earlier DB-written failures in the window, including `stream_http_404`; many other attempts logged `Lease lost ... aborting without DB write`, which did not consume the failure budget. The quarantine is possible because the feed-level budget counts consecutive DB-written failures across attempts, not only failures inside one ffmpeg process.

## Failure Budget Semantics

- VM runtime failure reporting increments `failure_count` and quarantines when the configured threshold is reached. The threshold observed in code/tests is 5 consecutive feed-level failures.
- Collector-local retry budgets are separate. OpenMHz, for example, can try 10 transport reconnects inside one collector attempt; if all 10 fail, that becomes one feed-level failure.
- Successful heartbeat/progress resets failure count. Lease-lost logs explicitly say they abort without DB write and therefore should not count toward quarantine.
- Post-capture pipeline failures, especially Pub/Sub schema validation, are currently capable of consuming feed failure budget even though the feed source was not the root cause. That is the highest-priority policy mismatch for leadership to decide.
